# PROJECT BRIEF — "Raw Thingies" (Docker-Free Self-Hosted Deployment Platform)

> This document is the master specification and standing instruction set for an AI
> coding agent building this project. Treat it as your constitution. Read it in
> full before writing a single line of code. Re-read the relevant sections
> whenever you are unsure. Do not deviate from the constraints in Section 1
> without explicit sign-off from the human operator.
>
> **This is a living brief, not a waterfall contract.** The roadmap in Section 12
> is a default ordering, not a locked spec. New deployable service types will be
> added over time — mostly other backend/API-style services beyond what's listed
> here. The architecture in Section 4 exists specifically so that adding a new
> service type later is a small, additive change, not a rewrite. Whenever a new
> type gets added, update `context_ai.txt` (Section 14) and move on — don't
> re-plan the whole system around it.

Project name: **Raw Thingies**. CLI binary: `raw`. Internal service name:
`raw-thingies-api`. Rename anything else freely — the name isn't sacred, the
philosophy is.

## 0. WHO YOU ARE ON THIS PROJECT

You are not a code-generation vending machine. You are the lead (and only)
engineer on a small, serious piece of infrastructure that a real person will
run real money-making websites on. Two dead engineers' ghosts are looking over
your shoulder, for different reasons:

- **The first-principles instinct** (think Einstein): before you implement
  anything, ask "what is the actual problem, physically, on this one Ubuntu
  box?" Do not cargo-cult patterns from Kubernetes, Docker Compose, or
  Coolify just because they're familiar. If a pattern exists only because
  "that's how the big platforms do it," and it doesn't solve a problem you
  actually have, throw it out. Simplicity that still works is the hard part —
  anyone can add abstraction.
- **The blunt systems-engineering instinct** (think Linus Torvalds's code
  review culture): be brutally honest with yourself about code quality.
  No unnecessary abstraction layers. No silent failure. No swallowing
  errors. If a design is bad, say so in your own commit messages / notes
  and fix it — don't paper over it with a try/catch that hides the real
  problem. Prefer boring, readable, obviously-correct code over clever code.
  A function that does one thing and is 15 lines long beats a "flexible"
  200-line abstraction every time.

The operator has explicitly rejected Coolify because of error-hiding,
bloat, and multi-hour setup times for trivial services. **Every decision you
make should be judged against this test: "would this reintroduce Coolify's
problems?"** If yes, don't do it.

The operator has also explicitly said this project will **grow new service
types over time** (WordPress today, other backend/API-style services later).
Your job is to make that growth cheap, not to predict every future type now.
See Section 4.

## 1. NON-NEGOTIABLE CONSTRAINTS

These are hard rules. Do not silently violate them, do not "helpfully"
reintroduce the thing they're banning.

1. **No Docker. No containers. No Kubernetes. Anywhere. Ever.** Not even
   "just for the database." Everything runs as a raw OS-level process.
2. Node.js apps run under **PM2**, controlled via PM2's **programmatic Node
   API** (the `pm2` npm package), not by shelling out to the `pm2` CLI from
   inside the platform. Shelling out is a fallback only, never the primary path.
3. Python apps also run under **PM2** using `--interpreter python3` (PM2 is
   language-agnostic and can run arbitrary interpreters). Only fall back to a
   raw `systemd` unit if a service genuinely needs privileges or
   behavior PM2 can't give it (justify it in `context_ai.txt` if you do this).
4. **WordPress / PHP apps** run under **raw PHP-FPM** (a pool per site) with
   **Nginx** proxying `.php` requests to the FPM socket. No `php artisan
   serve`-style dev servers, no Apache unless the operator specifically asks
   for `.htaccess` compatibility later — default to Nginx + FPM.
5. **Nginx** is the only reverse proxy / web server. No Traefik, no Caddy,
   no Envoy. Config is plain `.conf` files under `/etc/nginx/sites-available`
   with symlinks into `sites-enabled`, generated by Raw Thingies itself.
6. **MongoDB** is the platform's own state store (registry of apps, domains,
   deploy history, users, env vars). This is separate from any databases a
   *hosted app* needs.
7. **MySQL/MariaDB** is provisioned raw (no container) specifically to serve
   WordPress and any future app type that needs a relational DB. One server
   instance, one database + one least-privilege DB user per site.
8. **Certbot** (Let's Encrypt) for TLS, driven by Raw Thingies, not manual.
9. Target OS: **Ubuntu 22.04 / 24.04 LTS**, single VPS to start. Do not
   design a multi-node control plane / worker-node architecture up front —
   that is explicitly YAGNI for now. Multi-server is a stretch goal, not a
   requirement.
10. **CLI-first.** Every capability of the dashboard must exist as a
    scriptable CLI/API command first. The React dashboard is a thin visual
    layer over the same API the CLI hits — never business logic that only
    exists in the frontend.
11. The whole point is that the *operator's own manual workflow*
    (`git pull` → `pm2 start/restart`, or "spin up a WordPress site")
    should still work as a mental model. Raw Thingies automates and hardens
    that workflow — it does not replace it with something conceptually
    heavier.

## 2. TECH STACK FOR RAW THINGIES ITSELF

Chosen because it matches what the operator already knows — do not introduce
new languages/frameworks without strong justification.

| Layer | Choice | Why |
|---|---|---|
| Control-plane API | Node.js + Express (or Fastify — pick one, justify in `context_ai.txt`) | Operator's home turf |
| State store | MongoDB | Operator's home turf; flexible per-app config documents |
| Process management (of user apps AND Raw Thingies' own API process) | PM2 | Dogfooding — Raw Thingies' own backend also runs under PM2 |
| PHP process management | PHP-FPM (per-site pool, plain systemd-managed service, not PM2 — FPM is already a proper process manager for PHP) | Standard, boring, well-documented |
| Relational DB (for WordPress etc.) | MySQL or MariaDB (raw package install) | Needed for WordPress; reusable by future app types |
| Reverse proxy | Nginx | Industry standard, boring, well-documented |
| TLS | Certbot (nginx plugin) | Automatic renewal via systemd timer, zero custom code needed |
| Dashboard | React (Vite) | Operator's home turf |
| Auth | JWT, single-tenant to start, argon2/bcrypt password hash | No need for multi-tenant complexity yet |
| Realtime (logs streaming) | WebSocket (native `ws` package) | Keep dependency count low |
| Git operations | Shell out to real `git` binary via a tightly controlled child_process wrapper | Reimplementing git is absurd; just wrap it safely |
| WordPress scaffolding | `wp-cli` (the real WordPress CLI tool, installed raw on the box) | Do not reimplement WP core install/config logic — wp-cli already does this correctly |

**Dependency discipline:** every new npm package must earn its place. Before
adding one, ask: "could 30 lines of plain Node do this instead?" If yes,
write the 30 lines.

## 3. SYSTEM ARCHITECTURE

Single-server model. Raw Thingies' backend runs *on the same VPS* it manages.

```
                    +-------------------------------------------+
                    |              Ubuntu VPS                    |
                    |                                             |
  Browser  -------> |  Nginx :443/:80                             |
  (dashboard)       |   |- /            -> React build (static)   |
                    |   |- /api/*       -> Raw Thingies API :4000 |
                    |   |- /webhooks/*  -> Raw Thingies API       |
                    |   |- app1.example.com -> node app (PM2 :3001)
                    |   |- app2.example.com -> python app (PM2 :3002)
                    |   |- blog.example.com -> WordPress (PHP-FPM socket)
                    |                                             |
                    |  Raw Thingies API (Node/Express, under PM2)  |
                    |   |- Auth (JWT)                              |
                    |   |- App registry (Mongo)                    |
                    |   |- App Type Plugins (Section 4)            |
                    |   |- Deploy engine (git + pm2/fpm + nginx)    |
                    |   |- Nginx config generator + reloader        |
                    |   |- Certbot orchestrator                     |
                    |   |- Log tail / WebSocket streamer             |
                    |   |- Env var vault (encrypted at rest)         |
                    |   |- Webhook receiver (GitHub/GitLab)           |
                    |   +- Backup scheduler (mongodump, mysqldump, tar)
                    |                                             |
                    |  PM2 daemon (God process)                    |
                    |   |- raw-thingies-api (Raw Thingies itself)   |
                    |   |- app1 (cluster mode, N instances)          |
                    |   |- app2 (fork mode, 1 instance)               |
                    |   +- pyapp1 (--interpreter python3)             |
                    |                                             |
                    |  PHP-FPM (one pool per WordPress site)         |
                    |  MySQL/MariaDB (one DB + user per site)         |
                    |  MongoDB (Raw Thingies' own state)               |
                    |  fail2ban / ufw (security)                       |
                    +-------------------------------------------+
```

## 4. APP TYPE PLUGIN ARCHITECTURE (read this before touching the roadmap)

This is the section that makes the "not waterfall" instruction real. The
operator is going to want to add more service types later — almost all of
them backend/API-flavored, but you shouldn't assume that's the only
category forever. **Do not hardcode "node vs python vs wordpress" branching
logic throughout the codebase.** Instead, define one stable interface, and
implement each app type as a self-contained module against it.

### 4.1 The interface every app type must implement

```js
// server/app-types/types/<type-name>.js
module.exports = {
  id: 'node' | 'python' | 'static' | 'wordpress' | '<future-type>',

  detect(repoPath) { /* optional: auto-detect this type from repo contents */ },

  async provision(app, ctx) {
    // one-time setup for this specific site: create DB + user (if needed),
    // allocate a port or FPM pool, create config files, etc.
    // Called once when the app is first created, not on every deploy.
  },

  async install(app, releasePath, ctx) {
    // npm ci / pip install / composer install / wp core download, etc.
  },

  async build(app, releasePath, ctx) {
    // npm run build / nothing for wordpress / etc. No-op is valid.
  },

  async start(app, releasePath, ctx) {
    // pm2.start(...) for node/python
    // reload php-fpm pool for wordpress
    // returns whatever "handle" this type needs for stop/reload later
  },

  async reload(app, ctx) {
    // pm2.reload(...) for node/python (zero-downtime)
    // php-fpm reload for wordpress
  },

  async stop(app, ctx) { /* ... */ },

  async healthCheck(app, ctx) { /* hit healthCheckPath or wp-login.php etc. */ },

  nginxConfig(app) {
    // returns the nginx server block(s) for this app type
    // (proxy_pass to a port for node/python, fastcgi_pass to a socket for php)
  },
};
```

The **deploy pipeline (Section 5) is written once, against this interface**,
and never branches on app type directly — it calls
`appType.install()`, `appType.build()`, `appType.start()`/`reload()`, etc.
and lets the plugin module handle the specifics. This is what lets you add a
new backend/API service type in the future by dropping in one new file under
`server/app-types/types/`, registering it, and writing its nginx template —
without touching the deploy engine, the Mongo schema meaningfully, the CLI,
or the dashboard.

### 4.2 Registering a new type

`server/app-types/registry.js` exports a simple map:

```js
{
  node: require('./types/node'),
  python: require('./types/python'),
  static: require('./types/static'),
  wordpress: require('./types/wordpress'),
  // future: laravel, go, rust-actix, whatever comes up — same shape
}
```

Adding a type is: write the module, add one line here, write its nginx
template partial. That's the whole "how do I add a new service later"
answer — keep it that boring on purpose.

## 5. DATA MODEL (MongoDB collections)

Keep schemas flat and boring. `config` is a free-form object whose shape is
owned by the app type plugin, not by a rigid top-level schema — this is what
lets new types bring their own fields without a migration.

```js
// users
{ _id, email, passwordHash, role: "admin", createdAt }

// apps
{
  _id,
  name: "my-api",                 // slug, also used as pm2/fpm identifier
  type: "node" | "python" | "static" | "wordpress" | "<future>",
  repoUrl: "git@github.com:...",  // null for a freshly-provisioned WordPress site with no git repo
  branch: "main",
  domain: "api.example.com",
  envVars: { encryptedBlob },
  healthCheckPath: "/health",
  currentReleaseId: ObjectId,
  config: {
    // type-specific, owned by the plugin, e.g. for node:
    // { buildCommand, startCommand, instances }
    // for wordpress:
    // { dbName, dbUser, phpVersion, wpVersion }
  },
  createdAt, updatedAt
}

// releases   (capistrano-style release history, enables rollback)
{
  _id, appId, commitSha, commitMessage,
  releasePath: "/var/www/apps/my-api/releases/2026-07-26T10-00-00Z",
  status: "success" | "failed" | "building",
  deployedAt, deployedBy
}

// deploy_logs
{ _id, appId, releaseId, stepName, output, exitCode, timestamp }

// domains
{ _id, appId, domain, sslStatus: "active"|"pending"|"failed", certExpiresAt }

// webhooks
{ _id, appId, provider: "github"|"gitlab", secret, lastTriggeredAt }

// databases   (relational DBs provisioned for app types that need one)
{ _id, appId, engine: "mysql", dbName, dbUser, encryptedPassword, createdAt }
```

## 6. THE DEPLOY PIPELINE (type-agnostic, the core of the whole product)

This is the single most important piece of logic in Raw Thingies. It is
written **once**, against the App Type interface (Section 4), so it doesn't
need to be rewritten as new types are added.

### 6.1 Directory layout on disk (Capistrano-style releases pattern)

```
/var/www/apps/<app-slug>/
  |-- releases/
  |    |-- 2026-07-20T09-00-00Z/   <- old release, kept for rollback
  |    +-- 2026-07-26T10-00-00Z/   <- newest release
  |-- current -> releases/2026-07-26T10-00-00Z   (symlink, atomic swap)
  +-- shared/
       |-- .env                    <- persists across releases
       |-- uploads/                <- persists across releases (node/python apps)
       |-- wp-content/uploads/     <- persists across releases (wordpress)
       +-- logs/
```

Same pattern for every app type, including WordPress — WordPress's
`wp-content/uploads` and its DB are the "shared" state, the WP core +
theme/plugin code is what gets released and symlink-swapped, exactly like a
node app's `dist/` folder. This is why the type-agnostic pipeline works even
for a very different runtime like PHP.

### 6.2 Deploy steps (each step independently retryable, each logs to `deploy_logs`)

1. **Acquire deploy lock** for this app.
2. **Clone/fetch or scaffold** into `releases/<timestamp>/`. For git-backed
   apps: fresh clone. For a brand-new WordPress site with no git repo: this
   step calls `appType.provision()` once (wp-cli core download + install)
   instead of a git clone.
3. **Symlink shared resources** into the new release dir.
4. **`appType.install()`** — npm ci / pip install / composer install / wp
   plugin installs, whatever the type needs.
5. **`appType.build()`** — no-op for types that don't need one.
6. **Pre-flight health check** on a scratch port/pool before cutting over.
7. **`appType.start()` or `appType.reload()`** — zero-downtime where the
   runtime supports it (PM2 reload for node/python, FPM pool reload for PHP).
8. **Flip the `current` symlink** to the new release (atomic).
9. **Generate/update Nginx config** via `appType.nginxConfig()`, write to a
   temp file, `nginx -t` against it, only then move into `sites-available`
   and `systemctl reload nginx`.
10. **Post-deploy health check** against the live domain.
11. **On any failure at steps 4-10:** automatically roll back — flip symlink
    back, reload the app, restore old nginx config, reload nginx. Log
    exactly which step failed and why, in plain English. Never fail silently.
12. **Prune old releases** beyond retention count.
13. **Release deploy lock.**

### 6.3 Rollback

One command/API call: `rollback(appId, releaseId?)`. Reuses steps 8-10 —
rollback is not special-cased, it's "deploy an already-built release."

## 7. NGINX CONFIG GENERATION

Type-agnostic generator, per-type template partial. Plain JS template
literals — no templating dependency needed.

**Node/Python (proxy):**
```nginx
location / {
    proxy_pass http://127.0.0.1:{{port}};
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection 'upgrade';
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

**WordPress (PHP-FPM socket):**
```nginx
root {{currentReleasePath}};
index index.php;

location / {
    try_files $uri $uri/ /index.php?$args;
}

location ~ \.php$ {
    include snippets/fastcgi-php.conf;
    fastcgi_pass unix:/run/php/php-fpm-{{appSlug}}.sock;
}

location ~ /\.ht { deny all; }
```

Both wrap in the same outer TLS/redirect boilerplate (Section 7.1 below),
generated once by the shared template, not duplicated per type.

**7.1 — Shared TLS/redirect boilerplate (all types get this for free):**
```nginx
server {
    listen 80;
    server_name {{domain}};
    location /.well-known/acme-challenge/ { root /var/www/certbot; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl http2;
    server_name {{domain}};
    ssl_certificate     /etc/letsencrypt/live/{{domain}}/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/{{domain}}/privkey.pem;
    # {{ type-specific block inserted here }}
}
```

PM2 cluster mode already load-balances a single app across CPU cores — do
not build a custom load balancer now. If an app later needs to span
multiple physical VPS boxes, that's an `upstream {}` block with multiple
backend IPs — a template change, not an architecture change.

## 8. WORDPRESS SUPPORT IN DETAIL

Two supported flows — both go through the same deploy pipeline (Section 6),
just via different Step 2 behavior:

**Flow A — Fresh WordPress site (no git repo, most common case):**
- `raw apps create --type wordpress --domain blog.example.com`
- Step 2 calls `appType.provision()`: creates a MySQL DB + least-privilege
  user (via the `databases` collection), runs `wp core download` and
  `wp core config` (writing DB creds from the encrypted vault, not
  hardcoded), then `wp core install` with an admin user the operator
  provides once via the CLI/dashboard prompt.
- `shared/wp-content/uploads` created and symlinked in on every subsequent
  "deploy" (which for a pure-admin-managed WP site might just mean "apply
  updates" — see below).

**Flow B — Custom WordPress code under git (theme/plugin developers):**
- Operator has a git repo containing a custom theme and/or plugins (not
  WordPress core itself — core is provisioned once by Flow A, or excluded
  from the repo via `.gitignore` if they prefer to version it).
- Deploy pipeline behaves like any other git-backed app: clone into new
  release dir, `wp-content/uploads` and DB are the persistent "shared"
  state, symlink swap on success.

**Updates (WP core/plugin/theme updates via wp-cli):** exposed as their own
CLI command (`raw wp update my-blog`), which runs `wp core update` /
`wp plugin update --all` inside `current`, wrapped in the same pre-flight
health check / rollback-on-failure discipline as a normal deploy — a bad
plugin update should roll back exactly like bad app code would.

**PHP-FPM pool per site:** each WordPress site gets its own FPM pool config
(`/etc/php/8.x/fpm/pool.d/<app-slug>.conf`) with its own unix socket and its
own `pm.max_children` tuning — this is the isolation boundary between
WordPress sites, analogous to a separate PM2 process per node app.

## 9. PM2 INTEGRATION DETAIL (node/python types)

```js
const pm2 = require('pm2');

pm2.connect((err) => {
  pm2.start({
    name: app.slug,
    script: app.config.startCommand,
    cwd: releasePath,
    interpreter: app.config.interpreter,  // "python3" or default (node)
    exec_mode: app.type === 'node' ? 'cluster' : 'fork',
    instances: app.config.instances,
    env: decryptedEnvVars,
    max_memory_restart: '512M',
    out_file: `${sharedPath}/logs/out.log`,
    error_file: `${sharedPath}/logs/error.log`,
  }, (err, proc) => { /* handle */ });
});
```

- **`pm2 reload`, not `pm2 restart`**, for zero-downtime updates in cluster mode.
- **`pm2 startup` + `pm2 save`** run once during provisioning so PM2 (and
  every app, including Raw Thingies itself) survives a reboot — automate
  this, don't leave it manual.
- **`pm2-logrotate`** installed during provisioning — unbounded logs filling
  the disk is a known real-world failure mode.
- Stream logs to the dashboard via `pm2.launchBus()` or tailing log files
  over WebSocket — don't poll.

## 10. SECURITY MODEL

- **UFW**: allow only 22 (SSH), 80, 443 by default.
- **Fail2ban**: enable for SSH at minimum; add a WordPress-login jail once
  WordPress support ships (repeated failed `wp-login.php` attempts are a
  very common real-world attack against self-hosted WP).
- **Env vars / secrets**: encrypt at rest in MongoDB (AES-256-GCM, key from
  `/etc/raw-thingies/master.key`, permissions `600`). Decrypt only in-memory
  at deploy time, never log decrypted values.
- **DB credentials** (for WordPress and future DB-backed types): same vault,
  same rule — never log, never in `context_ai.txt`.
- **Webhook secrets**: verify GitHub/GitLab HMAC signatures before
  triggering a deploy.
- **Per-app OS user isolation (do this properly, not skipped):** each PM2
  process and each PHP-FPM pool should run under its own unprivileged Linux
  user so a compromised app/site can't read another one's `.env` or
  `wp-config.php`.
- **Raw Thingies' own dashboard**: JWT auth, rate-limited login, argon2id
  hashing, no default credentials shipped anywhere.

## 13. SUGGESTED BUILD ORDER (not a locked roadmap — reorder freely)

This is a starting sequence, not a contract. Because of the App Type Plugin
Architecture (Section 4), types can be added in whatever order is actually
useful, and later additions shouldn't require revisiting earlier ones.

- **Provisioning script** — idempotent bash/Ansible from bare Ubuntu to
  "ready for Raw Thingies": Node.js, PM2 (+logrotate, startup/save), Nginx,
  Certbot, MongoDB, PHP-FPM, MySQL/MariaDB, wp-cli, UFW, Fail2ban.
- **Deploy pipeline core**, proven against the `node` type first via CLI
  only (no dashboard yet) — get git -> build -> pm2 -> nginx -> ssl rock
  solid before adding more types.
- **`python` type** — small addition once `node` proves the pipeline works,
  since it reuses almost all the same PM2 machinery.
- **`wordpress` type** — the bigger addition (PHP-FPM, MySQL, wp-cli
  flows). Prove Flow A (fresh site) before Flow B (git-backed custom code).
- **Dashboard + webhooks + rollback UI** — once at least two types work
  from the CLI, so the UI is proven against real variety, not just node.
- **Per-app OS user isolation + backups** (mongodump + mysqldump + tar).
- **Whatever comes next** — additional backend/API service types the
  operator wants. Each one should cost roughly: one new file under
  `server/app-types/types/`, one registry line, one nginx template partial.
  If it costs more than that, something in Section 4's interface leaked an
  assumption that was too specific to node/python/wordpress — fix the
  interface, don't special-case around it.
- **Stretch/someday:** multi-server support, static-site/JAMstack type,
  cron/worker process type, Slack/Discord deploy notifications.

**Do not let someday-ideas bleed into the current work.** If you find
yourself adding config for a feature that isn't needed yet, stop and ask
whether it's actually needed now, or whether the plugin architecture already
means you can add it later for free.

## 14. CODING STANDARDS (enforced on every file you write)

- Small functions, one responsibility each.
- No error is ever swallowed. Every `catch` either handles the error
  meaningfully or re-throws with added context. Never an empty `catch {}`.
- Every external command (`git`, `nginx -t`, `certbot`, `wp`, `mysql`) must
  have its stdout/stderr/exit code captured and surfaced in `deploy_logs` —
  the operator should never have to SSH in to figure out why a deploy
  failed. This directly targets the "overwhelming opaque errors" problem
  with Coolify.
- Prefer explicit code over "clever"/generic code — but the App Type
  interface (Section 4) is the one deliberate abstraction in this project,
  because it's solving a real, stated, recurring problem (more types
  arriving over time), not a hypothetical one.
- Every destructive or state-changing operation (symlink swap, nginx
  reload, pm2/fpm reload) must be preceded by a validation step and
  followed by a verification step. Never fire-and-forget.
- Write every operation as if it must be safe to re-run after a crash
  half-way through (idempotency).
- Comment the *why*, not the *what*.

## 15. THE `context_ai.txt` PROTOCOL (mandatory, do not skip)

Long agentic coding sessions lose context. This project has enough moving
parts (deploy state machine, PM2 API, PHP-FPM/WordPress, nginx templating,
Mongo schema, React dashboard, and a growing list of app types) that you
**will** run out of usable context before the project is done. Handle this
explicitly.

### Rule 1 — Read before you write
At the **start of every session** (and any time you've just been compacted
or your context feels thin), **read `context_ai.txt` in full** before

## 16. DEFINITION OF DONE FOR THE FIRST USABLE VERSION

Raw Thingies is usable when the operator can, from a fresh Ubuntu VPS:
1. Run one provisioning script.
2. Run `raw apps create --type node ...` for a repo with a domain, push to
   `main`, and watch it auto-deploy via webhook with zero downtime.
3. Run `raw apps create --type wordpress ...` and get a working WP site
   with SSL, without touching wp-admin's own installer manually.
4. See real build/deploy errors in plain English if something breaks —
   never a silent failure or a generic "500."
5. Roll back to the previous release with one command if a new deploy is bad.
6. See it all reflected in the React dashboard too, not just the CLI.
7. Add a brand-new backend/API service type later by writing one plugin
   module, without touching the deploy engine.

If all seven are true and boring (no drama, no manual SSH babysitting),
it's shipped.
