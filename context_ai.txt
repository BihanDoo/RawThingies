## 1. WHAT RAW THINGIES IS (one paragraph, unchanging)
Raw Thingies is a Docker-free, self-hosted deployment platform and control plane that manages raw OS-level processes. It provisions its own infrastructure, manages Node.js and Python apps via PM2, sets up WordPress apps via PHP-FPM, and automates Nginx + Certbot for SSL, all without containers.

Reaching it from another LAN device requires port 4000 open (see below) - this deviates from brief Section 10's "only 22/80/443" model, on purpose, as a v1 shortcut.
- [2026-07-29] PROVED the full pipeline on a real Ubuntu 26.04 VM (raw@192.168.0.105, LAN test box). Found and fixed 4 more real bugs in the process, in order encountered:
  1. Root `node_modules` on the VM predated the `express` dependency - just needed `npm install` re-run after pulling. Not a code bug, a stale-install trap.
  2. Rollback logic in `deploy()` called `fs.readdirSync(releasesPath)` unconditionally in the catch block; if deploy failed before that directory was ever created (e.g. a permission error), this threw a NEW unhandled error that masked the real one. Fixed: guard with `fs.existsSync(releasesPath)` first.
  3. `/var/www/apps` was created by `install.sh` as root:root 755, but the control-plane process correctly runs as an unprivileged user (not root) - so it couldn't write releases into it. Fixed: `install.sh` now chowns `/var/www/apps` to `$SUDO_USER` (the operator who ran the script via sudo).
  4. `node` app-type's `start()` used PM2 `exec_mode: 'cluster'` with `script: 'npm start'`. Cluster mode requires a real requireable Node entry file - it silently fails (process shows as errored, but BOTH stdout and stderr log files stay empty) when given an npm/yarn wrapper command. Fixed: switched to `exec_mode: 'fork'`, `instances: 1`. Cluster mode may be worth revisiting later, but only once app-type config has a proper "entry file" concept separate from "start command" - forcing cluster mode onto arbitrary start commands doesn't work.
  5. Writing `/etc/nginx/sites-available/*` and running `systemctl reload nginx` both need root, but (correctly) the control plane doesn't run as root. Fixed properly, not hacked around: `install.sh` now chowns just `sites-available`/`sites-enabled` to the operator, and installs a narrowly-scoped `/etc/sudoers.d/raw-thingies` rule - NOPASSWD for exactly `/usr/sbin/nginx -t` and `/usr/bin/systemctl reload nginx`, nothing else, validated with `visudo -c` before install so a bad rule can't break sudo. `deploy/index.js` now calls `sudo nginx -t` / `sudo systemctl reload nginx`. The operator applied the sudoers/chown step manually via SSH (Claude Code's safety classifier correctly blocks automated sudoers.d writes over a remote SSH session - this is the right call, don't try to route around it again; hand the operator the exact commands instead).
- [2026-07-29] Test app used for the proof: `~/test-apps/hello-node` on the VM itself (plain git repo, not on GitHub) - a minimal `http` server with `/health`. Deployed as app name `hello-node`, domain `hello-node.local` (fake, LAN-only, no real DNS - verified via `curl -H "Host: hello-node.local"` instead).

## 8. KNOWN ISSUES / TECH DEBT
- Health check happens AFTER PM2 cutover/reload, not before (brief Section 6.2 step 6 calls for a pre-flight check on a scratch port before cutover). A bad release currently goes live briefly before rollback triggers.
- First-deploy failure has no rollback target (no previous release exists yet) - app is left partially started with a symlink pointing at a broken release.
- Dashboard v1 has no auth - must not be exposed outside a trusted LAN as-is.
- Dashboard is reached on port 4000 directly, not proxied through Nginx on 80/443 - requires opening 4000 in UFW (done, scoped to the LAN /24 subnet on the test VM). Should eventually get a real Nginx vhost like any other reverse-proxied service, per brief Section 3's architecture diagram.
- No deploy lock (concurrent `raw deploy` / dashboard-deploy-button clicks on the same app could race).
- `deploy()`'s `isFirstDeploy` check is `!fs.existsSync(currentPath)` - it infers "is there already a running process" from a symlink's existence, not from asking PM2 directly. If the `current` symlink exists but the PM2 process was deleted/crashed outside the normal flow (e.g. manual `pm2 delete`, or a reboot without `pm2 resurrect`), deploy() calls `plugin.reload()` on a process PM2 has no record of and fails with "process or namespace not found". Hit this exact case during testing (self-inflicted via manual pm2 delete) - not yet fixed properly, worth doing before this is trusted unattended.
- No UI/CLI validation yet that a `--repo` path/URL is actually reachable before attempting deploy.
- MongoDB apt repo in install.sh is hardcoded to `jammy` (22.04) regardless of actual host codename - worked fine on the Ubuntu 26.04 test VM (MongoDB's repo commonly lags newest Ubuntu releases, jammy packages install fine on newer hosts), but hasn't been stress-tested beyond that.

## 9. THINGS TRIED AND REJECTED (don't redo these)
- Rejected `commander` for CLI args parsing; vanilla `process.argv` is sufficient for current scope.
- Rejected WebSocket log streaming for dashboard v1 in favor of simple polling, to keep v1 dependency-light. Revisit for full Section 12 scope.
- Rejected building a full Nginx vhost for the dashboard itself in v1; serving it directly off Express on :4000 instead. Revisit once ready to harden.
- Rejected running the whole raw-thingies-api process as root to sidestep the /var/www/apps and /etc/nginx permission issues. Instead: chown the specific directories the control plane needs to write, plus a narrowly-scoped sudoers rule for the two commands (nginx -t, systemctl reload nginx) that genuinely need root. Keeps blast radius small if the control plane is ever compromised.
- Rejected sshpass/expect/plink for scripting password-based SSH from the Windows dev machine (none installed, and installing a password-piping tool felt like the wrong default). Used Python + paramiko instead (pure-Python SSH client, supports password auth natively without a pty). This was for AUTOMATING the VM during development/testing only - not part of the shipped product.
- Rejected an SSH keypair for the test VM per operator's explicit instruction ("don't create any keys, just use password... this is not going out of my firewall"). Password auth only, for this LAN-only test box.
