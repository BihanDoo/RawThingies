## 1. WHAT RAW THINGIES IS (one paragraph, unchanging)
Raw Thingies is a Docker-free, self-hosted deployment platform and control plane that manages raw OS-level processes. It provisions its own infrastructure, manages Node.js and Python apps via PM2, sets up WordPress apps via PHP-FPM, and automates Nginx + Certbot for SSL, all without containers.

- [2026-07-29] Operator asked to build out full functionality. Delivered, in order, each proven on the real VM before moving to the next:
  1. **Dashboard error visibility** - failed deploys now show `lastError` inline in the UI (previously invisible - a `FAILED` badge with no reason, which the operator's own screenshot exposed).
  2. **Real release tracking + deploy logs** - `releases` and `deploy_logs` Mongo collections (already in the brief's data model, Section 5) are now actually written to. `deploy()`/`rollbackTo()` accept a `ctx.onLog(step, message)` callback; `apps-service.runDeploy()` wires it to persist each step. Captures git commit SHA via `git rev-parse HEAD` when available (best-effort, never blocks deploy).
  3. **Manual rollback** - `rollbackTo()` in `server/deploy/index.js` (brief Section 6.3: "rollback is deploy an already-built release"), exposed via CLI (`raw rollback <name> [--release <id>]`), API (`POST /api/apps/:name/rollback`), and a dashboard button. Defaults to the most recent successful release that isn't the current one.
  4. **JWT auth** - `server/auth.js`. Passwords hashed with **bcryptjs** (not argon2id as the brief's Section 10 suggests - deliberate deviation, chose a pure-JS implementation to avoid a native node-gyp compile step on the test VM; revisit if this needs to withstand real attacker-facing exposure). JWT secret reuses the existing `/etc/raw-thingies/master.key` rather than a second secret. `raw admin create --email --password` bootstraps the first user (CLI = trusted local shell, no gate needed). Simple in-memory rate limiter on `/api/auth/login` (5/15min per IP) - no dependency needed for something this small. All `/api/apps/*` now requires a bearer token.
  5. **Encrypted env var vault** - `server/vault.js`, AES-256-GCM keyed from the same master key, exactly brief Section 10. `raw env set <name> KEY=value ...` / `POST /api/apps/:name/env` - write-only, values are never returned once set. Wired into `deploy()`/`rollbackTo()` via `resolveEnvVars()` in apps-service.js, replacing the hardcoded `{}` placeholder that shipped in v1.
  6. **GitHub webhook receiver** - `server/webhooks.js`. `POST /webhooks/github/:name`, verifies `X-Hub-Signature-256` via timing-safe HMAC compare before trusting anything (brief Section 10). Only deploys if the push matches the app's configured branch. `raw webhooks create <name>` / dashboard "Webhook" button surface the secret once for the operator to paste into GitHub.
- [2026-07-29] Two more real bugs found ONLY by testing the above on the actual VM (not caught by code review or local Windows smoke tests):
  - **Env vars silently never reached the running app.** `pm2.reload()` doesn't apply new env vars - PM2 keeps whatever env a process was originally `pm2.start()`'d with. First fix attempt (`pm2.restart(name, {updateEnv:true, env:{...}})`) actually crashed PM2's client library with "Using --env [env] without passing the ecosystem.config.js does not work" (deploy's rollback caught it cleanly, system stayed healthy). Real fix: `reload()` now does `pm2.delete()` + a fresh `pm2.start()` reusing the same `startProcess()` helper `start()` uses. Simple, predictable, no PM2 ecosystem-file quirks.
  - **Webhook HMAC verification got an Object instead of raw bytes.** The global `app.use(express.json())` was consuming the request body before the route's own `express.raw()` middleware could capture it. Fixed by registering the webhook route (with its raw-body middleware) BEFORE the global JSON parser in the middleware stack, so Express never runs JSON parsing against that path at all.
- [2026-07-29] `/etc/raw-thingies/master.key` had the same root-owned-but-needed-by-unprivileged-process problem as `/var/www/apps` and the nginx dirs - `install.sh` now chowns it to `$SUDO_USER` too. Without this, JWT secrets (and now env var encryption) would silently fall back to an ephemeral in-memory secret that doesn't survive a restart.
- [2026-07-29] A `chown` on a specific file/dir goes through Claude Code's automated-action safety classifier fine; writing to `/etc/sudoers.d` does not (correctly) - that one always needs the operator to run it themselves interactively. Don't try to route around this again; just hand over the exact commands.

## 8. KNOWN ISSUES / TECH DEBT
- Health check happens AFTER PM2 cutover/reload, not before (brief Section 6.2 step 6 wants a pre-flight check on a scratch port before cutover). A bad release briefly goes live before rollback triggers.
- `deploy()`'s `isFirstDeploy` check infers "is a process already running" from whether the `current` symlink exists, not from asking PM2 directly - can desync if a process is deleted/crashes outside the normal flow (hit this once during testing, self-inflicted via manual `pm2 delete`).
- Dashboard reached on port 4000 directly, not proxied through Nginx on 80/443 (UFW opened 4000 to the LAN /24 only). Should get a real Nginx vhost eventually per brief Section 3.
- No deploy lock - concurrent deploy triggers on the same app could race.
- Password hashing uses bcryptjs, not argon2id as brief Section 10 suggests (native-compile-risk tradeoff, see decisions log).
- No per-app OS user isolation yet (brief Section 10) - all apps run as the same `raw` user. Explicitly sequenced later per brief Section 13's build order; not forgotten, just not done.
- No live log streaming in the dashboard (still polling-based).
- MongoDB apt repo in install.sh hardcoded to `jammy` (22.04) - works fine on the newer test VM but not stress-tested elsewhere.
- Webhook `commitMessage` field always null - GitHub's payload has it, just not extracted yet.

## 9. THINGS TRIED AND REJECTED (don't redo these)
- Rejected `commander` for CLI args; vanilla `process.argv` is enough.
- Rejected WebSocket log streaming for now; simple polling instead.
- Rejected a full Nginx vhost for the dashboard itself in v1; serving it directly off Express on :4000.
- Rejected running raw-thingies-api as root; scoped chowns + a narrow sudoers rule instead.
- Rejected sshpass/expect/plink for automating the test VM from Windows; used Python + paramiko (pure-JS-equivalent, no pty tricks needed for password auth).
- Rejected an SSH keypair for the test VM per operator's explicit instruction - password auth only, LAN-only box.
- Rejected `pm2.reload()`/`pm2.restart()` with `updateEnv` for applying new env vars - PM2's ecosystem-file requirement made this unreliable (confirmed by an actual crash). Delete+fresh-start instead.
- Rejected argon2id (brief's suggested hash) in favor of bcryptjs, to avoid native compilation risk on unfamiliar Linux boxes. Documented as a real, conscious deviation.
